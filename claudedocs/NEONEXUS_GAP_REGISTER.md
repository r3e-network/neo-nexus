# NeoNexus Gap Register

139 verified findings consolidate to **47 distinct defects** in **6 themes**, generated by **3 root causes**. Ranked by operator impact within theme; themes ordered by how much damage the defect does to an operator under load.

The entries below are kept as written, as the record of what was found. **Status is tracked here**, at the top, so the register stays a description of the original state rather than becoming a half-edited mixture of past and present.

fabricated value named in Theme 1 is gone, and four gates keep it that way: no
page may state a verdict it did not compute, invent a measurement, name an actor
the journal does not record, or substitute a real duty for the absence of one.

**Root cause R2** — no observation layer — is closed. `src/observe/` samples
each node per class, derives, classifies into a nine-state machine, and persists
both the verdict and its transitions. Health is computed once and read
everywhere.

## Root causes

**R1 — The AWS costume is rendered as literals, not bound to state.**
The console was authored as a visual pastiche of EC2/CloudWatch/SSM/KMS. Where a real AWS console would bind a value, NeoNexus interpolates a string constant. This single decision generates ~20 of the register's entries, including all four Critical fabrications. The tell is structural: `fn active_alarms_table() -> String` (src/web/pages/alerts.rs:122) **takes no arguments**; `render_tab_monitoring` (src/web/pages/nodes/detail_tabs.rs:407) receives `&WebState` and `&[RpcHealthRecord]` and uses them only for `block_count`; `layout_with_density` (src/web/html/page.rs:59-65) has no fleet parameter yet renders a green `Health 2/2` pill on every page. It also generates the terminology sprawl: one signer binding wears five AWS service names, and the vocabulary borrowed (IAM/KMS/Instance Profile) teaches a wrong model because in AWS those are genuinely distinct services.

**R2 — There is no observation layer. The product has one chain read and no derived state.**
`src/rpc_health/probe/methods.rs:28-37` issues exactly two calls (`getversion`/`getblockcount`, or `web3_clientVersion`/`eth_blockNumber`), and `src/rpc_health/probe.rs:59-64` derives status from `ok_count`: how many of the two answered. Nothing anywhere compares successive heights, compares a height to a reference, times a request, counts peers on the health path, or evaluates a threshold. `RpcHealthRecord` (src/rpc_health/model/record.rs:4-13) has no latency and no peer field; there is no metrics history table at all (`grep -rn "metric" src/repository/` is empty). Consequently every alarm surface has nothing to bind to, alert routing can only express a severity floor, Prometheus has no chain dimension, and `syncing_nodes` had to be faked from a process state. R1 fills the resulting vacuum with green literals — R1 and R2 compound.

**R3 — Capabilities are implemented in core and wired to exactly one surface, with no parity gate.**
`src/chain_state/`, `WorkspaceSupportBundleExporter`, `WorkspaceBackupImporter`, `ConfigDriftDetector`/`ConfigReconciler`, `WorkspaceIntegrityChecker`, `preview_alert_route`, `FastSyncSnapshotCatalog`, `PrivateNetworkPlanner`/`DeploymentExporter`, `create_remote_server`, `NodeRole::designation()` — each is complete, tested, and reachable from at most one of {CLI, tests}. Nothing fails the build when a registered route has no nav entry, a form action names no route, an `EventKind` has no construction site (51 of 93), or two same-named adapter hierarchies coexist with the substantive one unused. The same absence lets derived state be recomputed per call site — chain identity in three modules, "expected schema" in two, the role fallback in four — so they drift.

## Theme 1 — Fabricated state (fix first; it actively ends investigations)

**G1. The Alerts page ships four hardcoded alarms permanently reading `● OK`, including block-height stall and peer-count-low.** *(merged: 4 findings)*
`src/web/pages/alerts.rs:122 fn active_alarms_table() -> String` takes no argument and returns a literal `vec![]`; every state cell is `html::raw_cell(r#"<span class="badge running">● OK</span>"#)` at :128, :139, :150, :161. Rows: :137 `NeoNode-BlockHeight-Stall` / :140 `ChainHeadDelta >= 5 blocks (30s) without progress`; :148 `NeoNode-PeerCount-Low` / :151 `ConnectedPeers < 3 for 2 consecutive evaluations`; :159 `NeoNode-SignerLease-Expiring` / :162 `SignerLeaseTTL < 300s threshold remaining`. Tiles are literals too (:80 `"0 In alarm"`, :81 `"4 OK"`), mirrored on the landing page (src/web/pages/home.rs:151-152). `ChainHeadDelta`, `ConnectedPeers`, `SignerLeaseTTL` appear nowhere else in src/. No alarm evaluator exists anywhere in the codebase. Note the raw quantities for three of the four *do* exist elsewhere (host CPU at monitor.rs:99, block height at probe/methods.rs:30, peer count at log_parsers/helpers.rs:76) — the page is disconnected from telemetry it already has. **Delete the table and the tiles; rename the destination to what is real (routing policy + `list_alert_deliveries` journal).**

**G2. Node detail "Monitoring" tab prints invented CPU, memory, latency, watchdog and four more green alarms.** *(merged: 4 findings)*
src/web/pages/nodes/detail_tabs.rs:417-431 — `"1.2% (Active)"`, `"64.5 MB"`, `"3.2 ms"`, selected only by `node.status.is_running()`, rendered under :483 `CloudWatch Instance Telemetry` / :484 "Near real-time instance metrics…" with provenance labels `Process private bytes` (:500) and `Loopback probe latency` (:510). The sparkline at :473 is a fixed literal path. :520 `Watchdog Armed (5 retries/60m)` contradicts the real, operator-editable policy (src/watchdog/policy.rs:3-5 — 3 attempts, 2s base, 30s cap, plus an `enabled` flag the badge ignores). :525/:529/:533/:537 are four unconditional `● OK` cards, including `● OK (Lease Valid)` on a function that receives no signer argument — so it reads green on a Consensus node the same page flags `requires Signer Lease` at :242. Real per-process CPU/RSS exist and are rendered honestly one page away (src/web/pages/monitor.rs:202-204 via `MetricsSnapshot::node_process`, src/metrics/types/snapshot/summary.rs:7). **RPC latency has no real counterpart anywhere in src/ — it must read "not measured", not be wired.**

**G3. The Health page draws a fake 60-minute chart and an unconditional `● Healthy` watchdog verdict, above inert controls.** *(merged: 3 findings)*
src/web/pages/monitor.rs:285 `<path d="M0,105 Q120,95 240,100 T450,70 T650,90 L800,{cpu_y} …"` — only the terminal point is live (:252-253), under axis labels :290 `-60m … Now` and caption :264 `1h Window · 1m Period`. No host metric is ever persisted: every consumer builds a throwaway `MetricsCollector::new(Duration::ZERO)` (metrics_page.rs:49, home.rs:107, workspace.rs:103, support_bundle/context.rs:79) and the interval-aware `refresh_if_due` (collector.rs:35) has zero callers. The 1h/3h/…/1w and Period pills (:84-95) are bare `<span>`s with a hover restyle (styles.rs:870) and no handler; `MonitorQuery` (:19-26) has no time field. :133 `● Healthy` is a constant that never reads `WatchdogStatus` (src/watchdog/model.rs:17-21), so it stays green while `WatchdogExhausted` (src/supervision/restarts.rs:152) sits in the journal. **Note: this page's CPU/memory *numbers* are real** — only the history, the selectors and the watchdog tile are fabricated.

**G4. All CPU percentages are deterministically stale, so the High-CPU filter never matches on a saturated host.**
Three `refresh_all()` calls back to back (collector.rs:20, :21, :30) with no interval; sysinfo 0.38.4 refuses to recompute CPU inside `MINIMUM_CPU_UPDATE_INTERVAL` (200ms), so the value freezes at the first sample — since-boot average on Linux, ~0 on macOS. Per-process CPU divides a near-zero delta by a stale global jiffy total and is then snapped to `0.0` by `clean_usage_percent`. Consequences: `src/metrics/filter.rs:81 row.cpu_usage_percent() >= 50.0` returns empty always, the CPU sort is inert, and `neonexus_system_cpu_usage_percent` cannot track load. **Hold one long-lived collector in shared state, refresh on the supervision tick, serve the last snapshot.**

**G5. The Configuration page reports "● In Sync" from `Path::is_file()` while advertising drift verification.**
src/web/pages/config.rs:142-146 and the "0 Drifted" tile at :113 derive from `row.managed_path.is_file()`; the header at :74 claims "configuration drift verification". The real SHA-256 + semantic comparator (`ConfigDriftDetector::check`, src/config/drift.rs:96-151) is reachable only from `--check-config-drift`. Mitigation: Start/Restart rewrite the managed config (src/node_lifecycle.rs:170), so the badge is wrong for edited-but-not-restarted nodes and for running nodes edited post-launch. Same page asserts encryption that does not exist: :97 "SecureString encrypted via AWS KMS default key" and :112 `("KMS Encryption", "AWS-KMS (active)")` — no AWS SDK in Cargo.toml, `grep -rni "encrypt" src/config/` empty. Files *are* 0600 (src/config/export/atomic.rs:114, :125), so the false negative is about disk encryption and backup exclusion, not permissions — and the generated configs embed **plaintext wallet unlock passwords** (src/config/generator/neo_cli.rs:116, neo_go/services.rs:57).

**G6. Status-check arithmetic is incoherent and absence counts as a pass.** *(merged: 3 findings)*

## Theme 2 — No chain observation (the product's stated job)

**G11. "Running but not syncing" is undetectable; health status is method-reachability.** *(merged: 5 findings)*
`src/rpc_health/probe.rs:59-64`. Height is fetched and stored with a timestamp (probe.rs:50-53; observability.rs:52-61) and *displayed* (fleet.rs:83 `healthy · block N`; detail_tabs.rs:291 trend table; :503 "Block Sync Height") but never compared to its predecessor, to a reference head, or to a clock. No `getblockheadercount`, `getbestblockhash`, or `eth_syncing` anywhere. A log-derived `SyncProgress { current_height, target_height, sync_percentage, peers_connected }` does exist (src/supervisor/model/log_parsers.rs:31-36) and reaches `GET /api/nodes/{id}/metrics` (api.rs:180-232) — but neo-rs has no parser (log_parsers.rs:229), **both Neo X parsers gate on strings the clients never emit** (geth: `"Chain imported"` + `block=` vs real `Imported new chain segment blocks=`; reth: `"Block #"` + `"state root"` + `targetheight=`), no HTML page renders it, and its event severity is hardcoded `Info` (process.rs:402). The parsers are covered by a tautological test whose fixtures were written to match the parser (tests/unit/supervision/tests.rs:167-206), which is why CI is blind to it. **Make head-lag a stored field on the health record; derive Degraded/Stalled from it; drive Neo X sync from `eth_syncing` rather than log text.**

**G12. `src/chain_state/` — governance, designation, peer and mempool telemetry — is complete and reachable only from a CLI that takes a hand-typed endpoint.** *(merged: 4 findings)*
`classify_connectivity` (peers.rs:171-177, `0 => Isolated`) and `classify_congestion` (mempool.rs:174-182) are implemented, tested, and drive CLI exit codes (chain.rs:89-93, :115-119) — and nothing else. No src/web/ file imports `chain_state`; there is no peer or mempool `EventKind` and no Prometheus family (`src/metrics/prometheus/families/` is system/processes/workspace/missing only). The CLI signature is `--peer-health <rpc-endpoint> [neo-n3|neo-x]` (chain.rs:102) even though `node_rpc_endpoint(node)` (rpc_health/probe/endpoint.rs:4) and `node_type.family()` both exist. Thresholds are compile-time constants: a 4-node private network reads "Healthy" at 3 peers; 500 tx reads "Elevated" on a chain configured for 5,000-tx blocks (config/format/network.rs:90-93). **Poll on the RPC-health schedule, persist per node, surface on the node page, key CLI commands by node id.**

**G13. Duty→designation is dead code: assigning Oracle/StateValidator/Notary never checks the chain, and designation is never remembered.** *(merged: 2 findings)*
`NodeRole::designation()` (src/roles/role/model.rs:94-103) has zero non-test callers. `designation_status` (chain_state/designation.rs:27) is CLI-only, asks only at current height, and takes an optional public key as argv — omitting it exits 1, identical to "not designated" (chain.rs:23-26 + model.rs:39-41). Nothing persists the answer: no `designation` in src/repository/, no event kind. Meanwhile `apply_role` (roles.rs:200-209) gates only on the local `role_availability` table. The node's key *is* derivable per node id (`node_signer_bindings`, inventory.rs:37-42 → node_signer.rs:209/:225/:270). **So NeoNexus cannot say "your Oracle designation was revoked at 03:14" — the case where a node keeps running and stops doing its job.**

**G14. Alert routing can express exactly one condition: a global severity floor.**
`AlertRoutingPolicy` (src/alerts/policy.rs:11-18) is five global settings keys; `should_route_alert` (routing.rs:8-15) never reads `event.node_id` or `event.kind`. One provider, one URL — "Critical to PagerDuty, Warning to Slack" is unexpressible; so is "page on the validator, warn on observers". Nothing numeric can enter the decision, because nothing numeric is evaluated (R2). Delivery is one event per 1s tick (alerts.rs:32, engine.rs:25). Partial mitigations that exist: a kind+node dedup key for PagerDuty/Opsgenie/Datadog (payloads/common.rs:16) and edge-triggered RPC-health events (health_events.rs:66-71). `preview_alert_route` (src/alerts/preview.rs:49) exists and is CLI-only, so a pasted webhook cannot be test-fired from the browser.

**G15. Documented Prometheus metrics do not exist and the real exposition has no chain dimension.**
docs/AGENT_API.md:266/271/276 document `neonexus_node_running`, `neonexus_node_block_height`, `neonexus_node_rpc_latency_seconds` — zero hits in src/. Actual output is fixed at src/metrics/prometheus.rs:26-29: 4 workspace + 6 system + 4 process gauges + `neonexus_node_missing_process`. Labels are node_id/node_name/pid/status only (labels.rs:4-8). A working `add_chain_labels` exists (neox_geth_adapter.rs:51) and is never called.

**G16. Two same-named metrics-adapter hierarchies; the substantive one (1,853 lines that can scrape a node's own `/metrics`) is never constructed.**
src/metrics/prometheus/*_adapter.rs vs the unit structs in src/supervisor/model/metrics.rs registered at adapters.rs:59-99. The live one only returns a URL string (web/api.rs:218). Neo X metrics URLs are hardcoded to ports nothing listens on — `http://localhost:8546/metrics` (geth's *WebSocket* default, which the repo itself calls out at neox/geth/model.rs:52) and `:9091` — and `_rpc_port` is discarded, so the value is a per-host constant that collides with two nodes. Neither launch path emits `--metrics` and neither config has a metrics key; `generate_config` is never called outside tests. **Wiring the substantive adapters would supply the block height and peer count Theme 2 is missing.**

**G17. `syncing_nodes` counts processes inside a ~600 ms launch window.**
src/web/public_api.rs:46 `count_status(&nodes, NodeStatus::Starting)`; `Starting`→`Running` transitions after `LAUNCH_SETTLE_WINDOW = 600ms` (supervisor/process/lifecycle.rs:25, node_lifecycle.rs:239-256). Rendered under a column literally headed "Syncing" (federation.rs:240, :259). Adjacent fields are honestly `None` (public_api.rs:47-49), which makes this the lone chain-word-on-a-process-counter. Federation's Blocks/Peers columns are consequently always `—` for the NeoNexus↔NeoNexus topology and every probe message ends `0 blocks` (federation/parsing.rs:49-51).

## Theme 3 — Configs that produce nodes which cannot work

**G18. Neo N3 nodes are rendered with no seed list and no committee, and readiness reports "ready".** *(merged: 2 findings; empirically reproduced)*
Every launch renders with `profile: None` (src/node_lifecycle.rs:170-175). Fallbacks: `Network::Private => Vec::new()` for seeds (config/format/network.rs:79) and committee (committee.rs:81), magic 1_230_000 (network.rs:13). Reproduced with `--generate-node-config`: neo-go private → `SeedList: []`, `StandbyCommittee: []`, **"ready, 10 pass, 0 critical"**; neo-rs private → `seed_nodes = []`, "ready, 24 pass"; neo-cli private → the entire ProtocolConfiguration is `{"Network": 1230000}`. neo-cli is worst because it *omits* the keys (generator/neo_cli.rs:71-76 writes SeedList/ValidatorsCount/StandbyCommittee only under a profile), so it falls back to compiled-in **public** defaults and dials mainnet seeds while carrying magic 1230000. Validation cannot catch any of it: neo_cli.rs:39 gates the committee checks on `profile.is_some()` and never checks SeedList; neo_go.rs:46 and neo_rs/p2p.rs:56 check `len >= 0`. Contrast the Neo X path, which does fail closed (diagnostics/checks/chain.rs:69-78). **Persist network identity (magic, seeds, committee, validators count) on the node or a network entity and derive the profile from the DB on every render, so Start and the launch pack produce byte-identical configs.**

**G19. Private-network chain identity is never persisted and the authoring path is unreachable.** *(merged: 3 findings)*
`RuntimeConfigProfile` (config/format/types.rs:8-14) is constructed in two places, neither reachable from web or CLI: private_network/exporter/writer/nodes.rs:33 and magic_override.rs:387. `PrivateNetworkPlanner::plan`, `PrivateNetworkPlan::to_new_nodes` and `PrivateNetworkDeploymentExporter::write` have **no callers in src/** — only tests. `PrivateNetworkMaterialized` / `PrivateNetworkLaunchPackExported` (events/kind.rs:49-50) are never emitted. The CLI can only *validate* a pack it cannot produce (`--validate-launch-pack`). The only whole-network record is the on-disk `DeploymentManifest` (private_network/schema/manifest.rs:9-25), never linked to workspace rows. And the nav item named "Private network" (nav.rs:85-90) opens the per-node duty support matrix (pages/roles.rs:49-55).

**G20. Three neo-cli duties are accepted, provisioned, and then never actually performed.** *(merged: 2 findings)*
StateValidator: the duty promises "Sign and publish state roots" (roles/role/model.rs:65), the plugin is enabled, the wallet is opened (`"IsActive": wallet.is_some_and(can_unlock)`, neo_cli.rs:119), the runtime root is verified — and `"AutoVerify": false` is hardcoded in a zero-argument `fn state_service()` (generator/neo_cli/sidecar.rs:192), pinned by a test at tests/unit/config/generator/neo_cli/sidecar/tests.rs:122. neo-go flips the same switch from the wallet (neo_go/services.rs:35,:45). Oracle: `"AutoStart": false` (:178) and `"Nodes": []` (:170) under a comment saying the operator fills it in — there is no field anywhere to fill it in, `GenerationContext` has no peers slot, and src/config/export/node.rs:187-208 rewrites every sidecar on each Start. `stdin(Stdio::null())` (supervisor/process/spawn.rs:32) denies the process the `start oracle` console command that would compensate. The dBFT sidecar in the *same file* varies `AutoStart` by signer (:202,:207), so this is asymmetry, not a platform limit. Readiness reports clean.

**G21. Neo X Consensus is offered and is structurally impossible to launch.**
`role_availability(NeoXGeth|NeoXReth, Consensus) => Supported` (roles/role/availability.rs:127) and `/roles` applies it. Launch then fails every way: no key → node_signer.rs:131-137; LocalWallet → :299-302 "uses NeoX key material and cannot consume a Neo N3 NEP-6 signer profile"; LocalSigner/NeoOsService → :307-313 "only neo-cli consensus is supported". The same dead end exists for neo-rs (:296-298). No `--validator`/`--miner` flag is emitted anywhere. **Derive the duty picker from what the launch path can produce, not from a hand-maintained matrix** — and note `role_availability` is consulted by *nothing* on the launch path despite roles.rs:2-4 claiming it is, so an unsupported duty (e.g. Oracle on neo-rs) is silently accepted and simply never takes effect.

**G22. Chain identity is computed in three places from a constant and never reconciled with operator flags.** *(merged: 2 findings)*
`neox_chain_id(node.network, profile)` is re-derived in the generator (neox/geth.rs:30), the validator (validation/runtimes/neox/geth.rs:15-16) and the readiness readout (diagnostics/checks/chain.rs:38) — all with `profile: None` at launch. `has_chain_argument` (chain.rs:85-91) tests only for a flag's *presence*; no flag-value extraction exists in src/. So after readiness blocks with "Add `--networkid <your chain id>`", one report can simultaneously acknowledge `--networkid 12345` and print "chain id 1230000". Worse, the blocker's stated reason is false for geth — the managed private config already pins a private id and kills discovery (geth.rs:26,:30,:49-50) — while the thing that actually matters (`geth init` against a genesis) is never verified, and `--datadir.chain` clears the gate while selecting nothing. For `Network::Private` the readout also asserts block period and validator count (format/neox.rs:75-87) as a **Pass** for a genesis NeoNexus explicitly refuses to generate.

**G23. Neo X peers, WebSocket, and the EVM surface are unaddressable.** *(merged: 3 findings)*
`static_nodes`/`trusted_nodes` are hardcoded empty (neox/geth.rs:51-52, reth.rs:48); private bootnodes are empty (format/neox.rs:38) with `--disable-discovery` (launch/neox.rs:89). There is no peer/enode field on `NodeConfig` and no form. Wiring is possible only through the free-text "Extra arguments" box, since `push_missing` (neox.rs:106) yields to operator flags and a `--config` arg bypasses the managed render — undiscoverable, not impossible. (And the geth validator raises a **false critical** for any non-empty private BootstrapNodes, validation/runtimes/neox/geth.rs:60-67.) A WS port set on a neox-rs node is validated (types/ports.rs:8), reserved against other nodes (port_planner/planner.rs:73), surfaced as `ws://127.0.0.1:{p}` and badged `Open` in the security-group table (detail_tabs.rs:596-602) — and never opened: no `--ws*` flag exists anywhere in src/. `HTTP_MODULES` is a 4-element const (geth.rs:17) and reth gets no `--http.api`, so the two Neo X clients expose different RPC surfaces for reasons the operator cannot see or change.

**G24. Promoting a neo-cli node to a signing duty always fails closed with an instruction the console cannot carry out.**
src/core/node_signer.rs:419-424 requires the binary's parent directory to equal the node working dir. Managed installs land in `<workspace>/runtimes/<type>/<version>/<platform>` and copy only the executable (runtime/package/installation.rs:44-63); plugins install under `<workspace>/nodes/<id>/Plugins` (plugins/manager.rs:62-66). **No chip the editor offers can ever satisfy the gate**, so Consensus/Oracle/StateValidator on neo-cli requires shell access to hand-place a runtime tree. Readiness does not run this preflight, so it surfaces only at Start.

## Theme 4 — Unreachable capability and dead ends

**G25. On a fresh workspace the entire runtime install path is unreachable, so there is no supported way to bring up a first node.**
`upsert_runtime_catalog_profile` (repository/runtime_assets/catalog_profiles.rs:4) has exactly one non-test caller: backup import (backup/workspace_importer/apply/profiles.rs:36). No route, no CLI flag, no schema seed. `/runtimes` renders `String::new()` (pages/runtimes.rs:319-320) and "No runtime catalog profiles are configured" (:407). The chain is circular — the upgrade policy requires a `catalog_profile_id` (runtime/policy/validation.rs:14) obtainable only from a backup of a workspace that could never have created one. **Ship a default Neo catalog profile as a schema seed and add an "Add catalog" form.**

**G26. Workspace backup cannot be exported *or* imported from the console.** *(merged: 3 findings)*
The page's only button posts to `/backup/export`; the only registered route is `POST /backup` (router.rs:169-170) and there is no fallback layer — so the click 404s and neither the archive nor the `BackupExported` event is produced. The page is in no nav section and no page links to it (its own handler passes nav key `"backup"`, which matches nothing). There is no import route at all; `WorkspaceBackupImporter::{validate_path, import_path}` are CLI-only, while the page promises the round trip at backup.rs:65. **Add a route-to-form parity test: every `control_form` action string in src/web/pages/ must resolve to a registered route.**

**G27. Restore quarantines every node with a blank binary path, and the stored original is never shown.** *(merged: 2 findings)*
restore.rs:54-55 writes `""` for binary_path and args, :66-73 stores the real values in `node_runtime_quarantine`. `quarantined_runtime_spec` (:98) is `pub(crate)`, not on `WorkspaceQueries`, and its only caller is the backup exporter — so the operator retypes argv the database is holding. The console *can* fix it (saving the editor clears quarantine, update.rs:53; chips auto-fill the binary, fields.rs:126) but the action is unnamed, the word "quarantine" appears nowhere in src/web/, the preflight message names a CLI flag (preflight/command_path/check.rs:15), and the one clickable remediation is misrouted: checks/binary.rs:20 tags `RuntimeResolution::RuntimeManager` → `/runtimes` (model/check.rs:107) instead of the `/nodes/{id}/edit` its own text names.

**G28. Signer backends exist only as process environment; registering one has no UI and needs a restart.** *(merged: 3 findings)*
`SignerRegistry::from_process_environment()` at startup (web/state.rs:217); the registry has no insert/reload. No route creates a `SignerBackendProfile`; importing a NEP-6 wallet stores metadata only (wallet_ops.rs:79). `binding.rs:182` says "Configure the signer registry before binding this node" with no link and no form. Once a backend exists, binding a node *does* work (POST /nodes/{id}/signer) — but the key id it demands as free text is not shown in the keys table (no key_id column, panels.rs:123), and the detail page shows the truncated *public key* instead; the id appears only in the URL and, for keys with audit history, in `label (key_id)` (overview/audit.rs:47). `sole_key_id` returns `None` for `NeoOsService` (registry/backend.rs:176), so there is no auto-fill for the case the whole /signer surface exists for, and a typo is caught only on first dispatch. There is no key rotation: `/signer/callers/{id}/rotate` exists, key routes are generate/delete/state/policy only — rotation is 8 manual steps across 6 pages with the node down throughout and no designation pre-check.

**G29. Federation servers can be listed and toggled but not created, edited, or deleted.**
Routes are read+toggle (router.rs:124-126). `create_remote_server` / `update_remote_server` / `delete_remote_server` are called only from tests; the sole production insert is backup import. The page tells the operator to write Rust (federation.rs:116). Every neighbouring entity has an in-page create form.

**G30. Nine core capabilities are CLI-only; the console cannot produce the artifacts an incident needs.** *(merged: 7 findings)*
Support bundle (`WorkspaceSupportBundleExporter::write`, sole caller cli/actions/reports.rs:104) — readiness + integrity + metrics + redacted log diagnosis in a checksummed zip, and the operator filing the ticket is the one least likely to have shell access; `EventKind::SupportBundleExported` exists so the console can *display* a bundle it cannot trigger. Readiness report and event-journal exports (`--export-readiness-report`, `--export-event-journal`) — /operations offers only a raw `/api/fleet` link, /events has a filter and no export even though `EventJournalReporter::write` accepts exactly the `RuntimeEventFilter` the page just applied. Workspace integrity check (`--workspace-integrity`) — computed for support bundles (`integrity_status`, support_bundle/model/manifest.rs:21), never shown live. Config drift + reconcile. Alert preview. Wallet validation report (web import calls `profile_from_path` only, so a wallet with WARNs imports with "imported successfully"). Snapshot catalogue browse + `compatible_entries` compatibility filter (implemented, zero callers) while /runtimes has a full catalogue→review→install flow. Release package verification.

**G31. Automatic runtime upgrade runs, but records nothing and ignores the policy checkbox it stores.**
The engine is real and wired (supervision/state.rs:109 → upgrade.rs), stops/downloads/installs/rebinds/restarts within a batch size and maintenance window. But it never calls `upsert_runtime_installation`, so /runtimes keeps listing old versions; every per-node failure is `warn!` only (:161,:178,:203,:236,:246,:254,:262) with the two fleet-level `record_event` calls carrying `node_id: None` — so /events shows "batch completed: 0/3 successful" with no reason anywhere in the browser; and `require_signed_catalog` (saved at policies/runtime_upgrade/save.rs:30, offered at settings.rs:243-248) has no reader in upgrade.rs, whose only consumer is a display string. There is no rollback: `update_node` overwrites `binary_path` with no prior value retained, and `RuntimeUpgradePlan.from_binary_path` (runtime/package/planning.rs:15) is reached only from tests.

**G32. The config text an operator needs to diagnose a crash loop is unreadable in the browser.**
/config renders a path (config.rs:147-151); `ConfigGenerator::render_for_node` is never called from src/web/ (only drift, export and diagnostics). The log-diagnosis remediation button routes back to /config (model/check.rs:104). Validator *findings* do surface on /operations (:137), but never the bytes. **Render the managed config inline, redacted through `redact_sensitive_text` as /logs already does, with a diff against disk.**

**G33. Stopping a crash loop means disabling automatic restart fleet-wide.**
One workspace watchdog policy (settings.rs:40, router.rs:219), read for every node (restarts.rs:29). The node page offers Start/Reboot/Stop/smoke only. Separately, the watchdog's *only* trigger is an unclean process exit (restarts.rs:74-75, :92) — `probe_rpc_health` never touches `self.watchdog` and `watch_external_processes` only marks a vanished PID Stopped. So it cannot act on an hour of Unreachable, and it cannot stop relaunching the node you are trying to edit.

## Theme 5 — Data model

**G34. A node cannot express where it runs.** No host/address/server column on `nodes` (inventory.rs:6-20); every endpoint is `http://127.0.0.1:{rpc_port}` (rpc_health/probe/endpoint.rs:4); the only spawn is local `Command::new`. Federation is a parallel, read-only universe of aggregate counters with no join to nodes. **A fleet is by definition multi-host; add `hosts` + `nodes.host_id` (default a seeded `local`) and make federation one transport among several.**

**G35. No history on nodes, and no timestamps.** `nodes` has no `created_at_unix`/`updated_at_unix` unlike every other entity (cf. observability.rs:12-13); `update_node` is a plain UPDATE that never loads the prior binary/version/ports; the upgrader's `from_version`→`to_version` pair appears only in a `tracing` macro (upgrade.rs:232), and `EventKind::RuntimeApplied` has zero emission sites. "What version was this on last Tuesday, what did we roll back from" is unanswerable. Restored nodes have no recorded add time (restore.rs emits no event).

**G36. 51 of 93 `EventKind` variants are never constructed.** Two flavours: operations that genuinely run and silently skip the journal (`--import-backup` and `--reconcile-node-config` mutate the workspace with no audit entry; also support-bundle, readiness, integrity, release verification), and kinds naming features with no caller at all (PrivateNetworkMaterialized, EventsPruned, the whole metrics/exporter family). The operator-facing consequence is narrower than a dead filter vocabulary, because /events has **no kind filter at all** — `EventKind::ALL` is referenced only from tests, and the page offers severity, free text and a row limit (events.rs:107-112), with no node select and no time bound. **Add a compile-time or test-time assertion that every variant has a construction site.**

**G37. Deleting a node drops its health rows and leaves its scoped token listed as Active forever.** delete.rs:19-28 deletes `rpc_health_checks` (≤24 rows, block height only — no latency is stored anywhere) and never touches `api_tokens`, which have no FK to nodes. The surviving credential is inert (UUID ids are never reused; namespace confinement + 404), so this is hygiene, not access — but nothing in the UI marks it orphaned.

**G38. Node name is a join key without a UNIQUE constraint.** No UNIQUE on `nodes.name` (inventory.rs:8); the launch-pack exporter keys by name (private_network/exporter/writer/nodes.rs:16-25) while uniqueness is checked only at plan time. Duplicate names silently write one member's config twice.

**G39. Structured grouping is one axis (role) plus free text.** No environment/tag/owner column; `NodeInventoryFilter` is `{status, query}` with substring matching over id/name/type/network (types/node_inventory.rs:33-45). Type and network are *not* filterable axes — only Status and Role are selects (list.rs:106-131). Alert routing therefore cannot be scoped to anything. Meanwhile the UI hardcodes an Environment tag (G7). Related: `node_roles` is one row per node, but `plugin_states` is genuinely many-to-many and is what drives neo-cli's emitted sidecars — the real single-duty limit is neo-go's exclusive `match role` over its four signing services (generator/neo_go/services.rs:33-39).

**G40. Data directory is expressible only as free-text args, and snapshot apply ignores it.** No data-path field; managed defaults are `<workspace>/nodes/<id>/`. Neo X honours an operator `--datadir` verbatim (launch/neox.rs:49,:109-113) and neo-go/neo-rs/Neo X honour `--config`; **neo-cli has no escape** (config_args.rs:5; `STORAGE_PATH_TEMPLATE` at neo_cli.rs:22,:93). Snapshot fast-sync always writes `<workspace>/nodes/<id>/data/<network>` (control/maintenance.rs:47-49), ignoring a custom datadir.

**G41. The integrity checker's required-table list has already drifted** — `workspace_integrity/schema/tables/core.rs` omits `node_signer_bindings` (whose unique index at migrations.rs:112 is the anti-double-signing constraint), `node_hermes_agents`, `node_runtime_quarantine`, `api_tokens`. Two hand-maintained declarations of one schema. **Derive expected schema from the creation statements.**

## Theme 6 — IA and terminology

**G42. Two competing navigations with different labels and coverage.** The sidebar (`nav::SECTIONS`) vs the `Services ▾` menu (html/page.rs:86-107): "Runtimes" vs "AMIs & Runtimes", "Configuration" vs "CloudFormation & Config", "Signer" vs "KMS Key Management". The menu omits Logs, Readiness, Federation, Roles, Wallets, Plugins, Metrics, Settings, and uniquely contains `/settings/api-tokens` — which has no nav entry despite marking Settings active, while Settings itself contains no `<a href>` at all. **Generate the menu from `nav::SECTIONS` or delete it.**

**G43. Up to four names per destination, and breadcrumbs that link to themselves.** `/monitor` = nav "Health", breadcrumb "CloudWatch / Metrics / All metrics" (both crumbs href `/monitor`), title "CloudWatch Metrics & Telemetry". `/config` = "Configuration" / "Systems Manager / Application Management / Parameter Store & Config" / "Systems Manager · Application Configuration" / "CloudFormation & Config". The word the operator clicked never appears on the page that opens. Six destinations (roles, plugins, wallets, settings, metrics, backup) have neither `page_head` nor breadcrumb; the Wallets import form is light-themed inside the dark shell (wallets.rs:120-132).

**G44. One signer binding wears five names; three unreconciled identity vocabularies.** "IAM Signer Lease" (detail_tabs.rs:81), "3. IAM SIGNER LEASE" (:348), "IAM Signer Role" with a KMS ARN as its value (list.rs:204+:180), "IAM Signer" (list.rs:401), "IAM Instance Profile & Signer Identity" labelling the actual control (node_editor/fields.rs:468), "Node signer" (binding.rs:187). Sidebar "Signer" → breadcrumb "KMS / Customer managed keys". "Wallets" is a fourth thing — except `SignerBackendKind::LocalWallet` is also called "Local encrypted wallet". "Lease" itself is **legitimate** (exclusivity is enforced at signing/isolation.rs:66-72, migrations.rs:112-113, node_signer.rs:160-172); what is invented is the TTL/AutoRenew vocabulary (alerts.rs:158-165) and the static "Lease Valid" tile. **Pick "signer binding" (node side) and "key" (custody side); delete the rest.**

**G45. Nav items name the wrong feature.** "Private network" → the duty matrix (G19). "EBS Snapshots" → *inbound* fast-sync archives, while the storage tab's "📸 Create Snapshot Backup" (detail_tabs.rs:698) points at it as if it captured state — the inverse direction — and the real workspace backup is unreachable (G26). "Consensus" vs "⚡ Validator" for the same duty on adjacent surfaces, with a role filter offering 5 of 8 duties (list.rs:123-130) so State/StateValidator/Notary nodes vanish from every filtered view.

**G46. Per-node context is dropped on every hop, and the one link that tries to carry it is broken.** `/logs?node=`, `/plugins?node=`, `/roles?node=` accept scope; `/monitor`, `/snapshots`, `/alerts`, `/config` do not. The node activity card links `/events?q={name}` (activity.rs:54) while the events search field is named `query` (events.rs:23,:109) — "View Full Audit Journal →" silently dumps the whole workspace journal.

**G47. Compact density silently breaks the instance drawer.** The drawer renders whenever any node is visible and is populated from `visible.first()` (list.rs:147-161); JS updates it from `tr[data-node-id]` (script.rs:282), which the comfortable table emits (:360) and the compact table does not (:458). On the density setting intended for large fleets, the drawer is pinned to node A while the operator believes they clicked node B. Also: Health and Metrics are the same `collect_snapshot` rendered twice, one of them a raw `<pre>` dump with no header and strictly less than the other.

## Suggested sequencing

1. **Delete every fabricated value** (G1, G2, G3, G5-KMS, G6, G7, G8-identity). This is a subtractive change, lands in days, and immediately stops the console lying during incidents. Adopt one rule: *no status word that is not a function of state*; enforce with a lint/review gate on literal `● OK` / `passed` / `Healthy` strings in src/web/pages/.
2. **Build the observation layer** (G11, G12, G16). One probe tick that stores height + head-lag + peer count + last-height-change per node; derived `Stalled`/`Isolated` states; a `metrics_samples` table. This is the prerequisite for real alarms, real charts, real Prometheus, a health-aware watchdog (G33), and scoped alert rules (G14).
3. **Make the first run work** (G25, G18, G26). Seed a catalog profile; persist network identity and render from it; fix the backup form action and add import.
4. **Add a parity gate** (root R3): registered GET route ⇒ nav entry or inbound link; `control_form` action ⇒ registered route; `EventKind` variant ⇒ construction site; core capability ⇒ declared surfaces. This is what stops Theme 4 from regrowing.
5. Data model (G34, G35), then IA/terminology (Theme 6) as a single naming pass once the surfaces are settled.
